Maintaining two Distributor APIs through the transition

The two APIs are facades over one canonical model, not two systems — this is the part that makes a dual-API period survivable rather than a maintenance burden:

  1. v1 is a translation layer, not a data store. It reads the same canonical record as v2 and reshapes it back into the existing XML field structure on the way out. There is never a separate "legacy" copy of the data to keep in sync — that's what makes the no-distributor-changes promise possible without a permanent double-write burden.
  2. Version by route, not by data. /v1/... and /v2/... sit behind the same gateway and the same auth/key model distributors already use, so switching is a URL change for a distributor when they're ready, not a new integration.
  3. Instrument usage before setting the retirement date. Track per-distributor v1 vs. v2 call volume from day one of v2's launch. The retirement date isn't a guess — it's set once the migration curve shows v1 traffic is low enough (and remaining holdouts are known and engaged), per the existing project constraint that this date is still TBD.
  4. Retirement is a deprecation window, not a flag day. Announce the date once set, support both through it, then turn v1 into a fixed-shape error response (not a silent 404) pointing distributors at v2 documentation.
